# 产品语域迁移 — Iris / Ash / Serif Display

这份文档只管一件事：**把 `DESIGN.landing.md` 的视觉系统推到产品语域（webapp + docs）**，让营销页和产品读起来是同一个品牌。

它是 `DESIGN.landing.md` §12 第 1、2 条的落地文档，与 `DESIGN.md` 的关系是：**本文描述迁移的目标态与每一步的 from → to，`DESIGN.md` 描述当前态**。迁移落地时按本文改写 `DESIGN.md` 的 §4 / §5 / §6，然后本文归档。在那之前，两份文档都有效，冲突时以 `DESIGN.md` 为准（它才是代码的真实描述）。

三条支柱，一句话各一条：

- **色彩** —— 中性轴从「石墨灰蓝」换成 landing 的 Ash（近中性），品牌轴从钢蓝换成 Iris。只换色相，不换明度。
- **文字** —— 引入 **Source Serif 4**（landing 真身用的族，不是文档里写的 Fraunces）做大标题。这一条推翻了 landing §12 的既有裁决，理由见 §4.1；文档与实现的漂移见 §4.0。
- **形状** —— 圆角**反向收紧**到 6 / 8 / 12（不是向 landing 靠）。色彩与字体收敛做品牌统一，圆角发散做密度区分。

怎么读这份文档：

- **要判断值得不值得**：§0.3 三处冲突 → §9 风险表。
- **要动手改**：§7 落地清单 → 每一项指回对应章节。
- **要知道数字怎么来的**：每张映射表下面的「怎么算的」。散文只解释 why，数字全部可复算。
- **要看效果**：仓库根的 `.product-iris.preview.html`（自带 前/后、浅/深、衬线 A/B、圆角 A/B 四组开关）。本文档与该 mock 冲突时，**以本文档为准**。

## 0. 范围与边界

### 0.1 本文档管什么

`:root` / `html[data-theme='dark']` 上的 `--color-*`、`--radius-*`、`--text-*` 三组 token，横跨两个基线文件：

| 文件                              | 角色                                           |
| --------------------------------- | ---------------------------------------------- |
| `apps/web/src/styles.css`         | webapp token 基线                              |
| `apps/web/tailwind.config.ts`     | webapp 圆角与字号族                            |
| `apps/docs/src/styles/global.css` | docs token 基线（字面量复制，不消费 `--lp-*`） |

### 0.2 本文档不管什么

**Fieldwork 不进产品。** ASCII 场、网点大气层、`<PixelMeter>`、sigil 头像 —— 一个都不迁。产品语域是功能性的，装饰层没有位置，而且 landing §3.4 的七条法则（墨阶、格子、12s 循环）在一个每天被读 8 小时的工作面上会变成噪声。`DESIGN.landing.md` §12 第 3 条列的那件事**明确不做**。

**密度不动。** 字号阶梯（32/22/20/18/16/14/14/12/12）、三档显示模式、控件高度、间距、`--text-chat` 契约、markdown 降一档规则 —— 全部照旧。迁移换的是**材质**，不是**尺度**。

**布局不动。** 侧栏宽度、容器宽度、断点、卡片栅格、页面结构，零改动。

**主按钮不动。** 产品的 `--color-strong` 是近黑石板（`10 12 15`），landing §1.7 的裁决也是近黑石板。**已经一致，不需要迁移。**

## 1. 中性轴：石墨灰蓝 → Ash

### 1.1 原则：只换色相，不换明度

产品的明度阶梯是精算过的 —— 每一档 hover 填充都按 **WCAG 对比度比值**（而不是 RGB 差值）反解过，`styles.css` 的注释里写着三个目标值：`surface-hover 1.146` / `rail-hover 1.108` / `soft 1.162`。那套阶梯承载的是**体积层级**（画布近白、rail 退后、卡片抬升），与色相无关，**不许动**。

要迁移的只有色相。两套轴的差别可以量化成一个数：**B − R 的偏移量**。

**关键：这个偏移不是常数，是明度的函数。** landing §1.2 表里那句「只留 2–4 单位的冷偏」说的是**背景五档**（`bg-deep` → `paper-warm`），不是整条 ramp。把它当成全局规则会读错这套系统 —— landing 自己的**墨阶**偏移大得多：

| landing token              | 值                    | B − R  |
| -------------------------- | --------------------- | ------ |
| `--lp-paper-warm`          | `#ffffff`             | 0      |
| `--lp-paper`               | `#fcfcfd`             | 1      |
| `--lp-bg` / `--lp-bg-soft` | `#f4f4f6` / `#f9f9fb` | 2      |
| `--lp-bg-deep`             | `#e7e8ea`             | 3      |
| `--lp-faint`               | `#b8b9bf`             | 7      |
| **`--lp-muted`**           | `#5c5e66`             | **10** |
| **`--lp-subtle`**          | `#8d8f97`             | **10** |
| `--lp-ink-soft`            | `#2a2b30`             | 6      |
| `--lp-ink`                 | `#101013`             | 3      |

规律很清楚：**离纯黑或纯白越远、越接近中灰，冷偏越大**，在 R ≈ 90–140 一带达到峰值 10。两端收敛到 0–3。深色模式是同一条曲线的镜像（`#050506` 是 1，`#1e1f23` 是 5，`#8c8e96` 是 10）。

这条曲线是有道理的：极亮和极暗处色偏本来就看不出来，硬加只会让白发蓝、黑发紫；而中灰是唯一能容纳可见冷偏又不显脏的区域，那点冷正是「纸」和「脏灰」的区别。

**做法**：对每个产品 token，固定其相对亮度 `L = 0.2126R + 0.7152G + 0.0722B`（线性化后），在 **landing 的十个中性锚点之间分段线性插值**出该明度应有的 `(B−R, G−R)`，再重解 RGB。不用全局公式拟合 —— 在 C ≈ 0.003 这个彩度水平上，1 个 RGB 单位就是 50% 的相对彩度差，公式的 ±1 误差会把逐字节对齐破坏掉。

### 1.4 hover δ 契约的验证

Ash 化之后，`styles.css` 注释里那三个目标比值必须仍然成立。实测：

| 关系                          | 现状比值 | Ash 后 | 偏差    |
| ----------------------------- | -------- | ------ | ------- |
| `surface-hover` on `surface`  | 1.1462   | 1.1425 | −0.0036 |
| `rail-hover` on `rail`        | 1.1069   | 1.1062 | −0.0008 |
| `soft` on `surface-elevated`  | 1.1630   | 1.1615 | −0.0015 |
| `surface-subtle` on `main-bg` | 1.1035   | 1.1041 | +0.0006 |
| `rail` on `app-bg`            | 1.1181   | 1.1263 | +0.0082 |

全部在 ±0.01 以内，即**远低于可辨阈**。结论：换色相不破坏体积层级，`DESIGN.md` §8.10 的按层级调 hover 那套逻辑原样有效，不需要重解。

> 这条验证是 `DESIGN.landing.md` §12 第 1 条特别点名的风险（「换轴时每个层级的 δ 要按对比度比值重解，不能照搬 RGB 差值」）。这里的做法比它要求的更强：**因为固定了相对亮度，δ 是自动守恒的，根本不需要重解**。

### 1.5 两处撞值

Ash 网格比石墨网格粗，两组原本差 1 个 RGB 单位的 token 会落到同值：

- `--color-soft`（`234 237 241`）与 `--color-surface-hover`（`233 237 241`）双双落到 `236 237 239`
- `--color-surface-subtle` 与 `--color-rail` 双双落到 `237 238 240` —— 这两个现在就是同值，不算新增

**保持它们是独立 token，不要合并。** 原本 1 个单位的差本来就在可辨阈以下（ΔL < 0.5%），撞值只说明它们在 Ash 网格上落到同一格；它们各自锚定不同的父背景（`soft` 在 `elevated` 上，`rail` 是侧栏底），未来任何一侧调整都需要独立的名字。`styles.css` 里那条「Do not use `--color-soft` on `--color-rail` backgrounds」的注释继续有效。

## 2. 品牌轴：钢蓝 → Iris

### 2.1 产品直接消费 landing 的十档 ramp

**不要为产品另配一支蓝。** landing §1.3 的十档 Iris ramp 按 OKLCH 校准过，整条 ramp 的彩度走一条弧、在 700 附近最高 —— 这是它能同时喂饱「浅底上的深文字」和「深底上的浅文字」的原因。产品照抄这十个值，一个不改：

```css
:root {
    --color-iris-50: 237 241 255;
    --color-iris-100: 219 227 255;
    --color-iris-200: 185 200 253;
    --color-iris-300: 140 165 249;
    --color-iris-400: 93 128 244;
    --color-iris-500: 66 107 240;
    --color-iris-600: 53 96 235;
    --color-iris-700: 24 66 216;
    --color-iris-800: 24 51 160;
    --color-iris-900: 21 36 102;
}
```

### 2.3 为什么深色取 300 而不是 landing 的 400

landing 深色主色是 Iris-400。产品**不能照抄**：400 在产品卡面（`35 36 38`）上只有 **4.33:1**，低于正文 AA 的 4.5。

产品与 landing 的差别在于卡片密度 —— landing 的品牌色主要出现在大字标题的强调词和按钮上，产品的品牌色出现在卡片内的链接、chip 文字、12px 的状态标签上，而这些几乎总是落在 `surface` 而不是画布上。

**别名下沉一档，档位值不变。** 这正是 landing §1.3 那条规则（「深色档位值不变，只有语义别名整体上移一档」）在更密语域上的自然延续，不是例外。真正需要 400 那种饱和度的填充场景走 `--color-info-vivid`，它不承载文字，不受 4.5 约束。

### 2.4 新增 `-vivid` 档的理由

landing §1.4 有一条很值钱的规则：**一支色两个亮度** —— `fill = 500 · numeral = 400 · label = ink-3`。填充条用饱和档，紧邻的读数退一档，一排计量条才不会变成色噪声。

产品现在只有 `-fg` / `-bg` / `-strong` 三档，其中 `-fg` 同时兼着「实心标记」和「状态文字」两个角色 —— 而这两个角色的对比度门槛不同（非文本 3:1 vs 文本 4.5:1）。合并的代价是：要么标记不够鲜活，要么文字不过 AA。**产品现在选的是后者**（见 §3.3）。

`-vivid` 把这两个角色拆开：**`-fg` 归文字与图标（≥4.5），`-vivid` 归纯填充（≥3.0）**。这是加法不是改法，现有调用点零迁移。

### 2.5 焦点环终于统一

`DESIGN.landing.md` §6.2 记了一个缺陷：`--shadow-focus` 的配方定义在 `:root` 上、消费 `--color-focus`，所以 landing 换成 Iris 之后**产品那枚焦点环仍然是旧钢蓝**，landing 只能自己另起一个 `--lp-shadow-focus`。

本轮迁移**自动修掉它**：`--color-focus` 指向 Iris-600 之后，两个语域的焦点环回到同一支色。

三件事保持不变：

- `--shadow-focus` 的**配方**不动（1px 实心核 + 4px @18% 光晕）。只有颜色变了。
- `test/focusRingContract.test.ts` 的门禁不动（所有 `shadow-focus` 工具类必须挂在 `focus-visible` 变体上）。
- **`--shadow-focus` 仍然是成对传播项**，webapp 与 docs 必须同版改。注意那个门禁在**父仓**、不在 oss（§7 的提示框）。

近黑石板（主按钮）上 Iris-600 的环看不见，与 landing 同样处理 —— 那些控件上把 `--color-focus` 覆盖成 Iris-300：

```css
.btn-strong,
[data-surface='inverted'] {
    --color-focus: var(--color-iris-300);
}
```

## 3. 判定色：取色相，守 AA

### 3.1 原则

landing 的四支判定色**不能直接照搬**。它们的文字档在产品画布上只有 2.55 – 4.17:1，全部不过 AA —— landing §1.4 自己承认这是「知情的低对比选择」，只允许出现在紧邻实心填充条的读数上。产品的状态色要用在独立的 12px caption 上，没有那个豁免。

**迁移的是色相与彩度，不是亮度。** 具体做法：取 landing 每支色的 OKLCH 色相角 H 与彩度 C，锁住 H，把亮度 L 求解到产品需要的对比度；彩度在色域边界处按需收紧（否则暗档的 C 会被裁掉，色相跟着漂移最多 12°）。

> **基准取自代码，不是取自 `DESIGN.landing.md` §1.4 的表。** 那张表的表头写「浅色 fill / text」，把 `#22c46f` / `#e9a23b` / `#f2554b` 列为浅色的 fill 档 —— **代码里没有这一档**。这三个值实际是**深色模式的 `-strong`**（`styles.css:2293/2296/2299`）。浅色的 `--lp-success` 就是单值 `#12a75c`（`styles.css:2100`）。照着那张表取基准会让 success 的彩度偏高 0.016、warning 的色相偏 3.4°。

|         | landing H | 产品现状 H | 色相差    | landing C | 产品现状 C |
| ------- | --------- | ---------- | --------- | --------- | ---------- |
| info    | 266.1°    | 250.9°     | **15.2°** | 0.215     | 0.130      |
| success | 153.5°    | 160.5°     | 7.0°      | 0.159     | 0.124      |
| warning | 68.9°     | 78.6°      | 9.7°      | 0.136     | 0.124      |
| error   | 28.0°     | 31.0°      | 3.0°      | 0.198     | 0.157      |
| idle    | 279.1°    | 258.4°     | **20.7°** | 0.031     | 0.015      |

landing 侧的取值：`--lp-info` = Iris-600、`--lp-success` `#12a75c`、`--lp-warning` `#c8811c`、`--lp-error` `#dd3d34`、`--lp-idle` `#9a9db2`（`styles.css:2092–2109`）。

真正看得出来的是两处：**info 的 15.2°**（钢蓝 → 鸢尾蓝）和 **idle 的 20.7° + 彩度翻倍**（中性灰 → 带紫的灰）。judgement 三支的色相差只有 3.7–7°，肉眼几乎不可辨 —— 它们的可见变化来自**彩度**（+15% 到 +42%），迁移后状态色会明显更鲜活。

idle 带紫是有意的：`#9a9db2` 在 279°，Iris 在 266°，同一个紫蓝家族。它让「禁用/空闲」读起来像品牌色退火之后的样子，而不是一支无关的灰。

`idle` 虽然没有文字调用点，仍然一并修 —— 它有 `-bg` / 状态点的用法，而且留一支不合规的颜色在 token 表里，下一个人就会用它。

迁移把五支全部拉到 4.58 – 4.96。这是本轮最实在的收益，也是即使不做 Iris 也应该单独做掉的事。

### 3.5 三档的角色定义 —— 写进规范，因为它现在是隐性的

| 档        | 角色                     | 对比门槛                      | 典型调用点                   |
| --------- | ------------------------ | ----------------------------- | ---------------------------- |
| `-bg`     | 低透明度底               | —                             | chip / badge 的填充          |
| `-fg`     | **文字与图标**           | ≥ 4.5:1 于其父背景            | `text-success`、状态点、图标 |
| `-strong` | 按压态、`-bg` 上的文字   | ≥ 4.5:1 于 `-bg`              | chip 内文字、hover 后的链接  |
| `-vivid`  | **纯填充，永不承载文字** | ≥ 3.0:1（WCAG 1.4.11 非文本） | 进度条、图表色、大色块       |

**`-vivid` 上不许放文字。** 它是这套系统里唯一一档知情地放弃文字对比的颜色 —— 与 landing §1.4 的 400 档读数是同一个性质。任何 `text-*-vivid` 的用法都是 bug。

判定色的两条既有硬规则继续有效，迁移不放松它们：

- **颜色永远不是唯一信号**（`DESIGN.md` §10.6）。每个状态必须同时带文字或图标。
- **不许新增第五种判定色**（`DESIGN.landing.md` §9.1 第 4 条）。

## 4. 文字：引入衬线 Display

### 4.0 先纠正一件事：landing 用的不是 Fraunces

`DESIGN.landing.md` §2.2–§2.4 通篇写的是 **Fraunces**（SOFT 50 / WONK 0 / 字重 300）。**代码不是这样。** landing 真身用的是 **Source Serif 4**：

|             | `DESIGN.landing.md` §2.2–2.4             | `src/styles.css` 实际                                                 |
| ----------- | ---------------------------------------- | --------------------------------------------------------------------- |
| 族          | `Fraunces Variable`                      | **`Source Serif 4 Variable`**                                         |
| 导入        | `@fontsource-variable/fraunces/full.css` | **`@fontsource-variable/source-serif-4/opsz.css`**（`styles.css:15`） |
| 依赖        | `@fontsource-variable/fraunces`          | **`@fontsource-variable/source-serif-4`**（`package.json:17`）        |
| 可变轴      | `SOFT 50, WONK 0` + opsz + wght          | **只有 opsz + wght**（Source Serif 4 没有 SOFT / WONK）               |
| 字重        | 300（卡片标题 400）                      | **400，统一**（`--lp-display-weight`）                                |
| tracking    | −0.014em（h2 −0.016em）                  | **−0.018em，统一**（`--lp-display-track`；h3 档单独 −0.008em）        |
| line-height | 0.98（h2 1.0）                           | **1**（`--lp-display-lh`；h3 档 1.14）                                |
| CJK 选择器  | `.landing-root:lang(zh)`                 | `html[lang^='zh'] .landing-root`                                      |

**字号阶梯是一致的**（h1 `clamp(46,6.6vw,100)` / h2 `clamp(34,4.2vw,60)` / h3 `clamp(24,1.9vw,29)`），漂移的是族与所有族参数。

这不是小事，因为**两种衬线的物理性质完全不同**：

- **Fraunces** 是高对比 display serif —— 主干与发丝笔画的粗细比很大，为大字号设计。它才是那条 24px 门槛（T1）的来源。
- **Source Serif 4** 是 Adobe 为**屏幕正文**设计的过渡型衬线 —— 笔画对比低、x 高度大、字面开阔。它的正常工作区间从 14px 起。

**本文档以代码为准**：产品迁移对齐 `Source Serif 4 Variable`。`DESIGN.landing.md` §2.2–§2.4 需要一个独立的修正 PR（§10）。

### 4.1 这是对 landing §12 第 1 条的推翻

`DESIGN.landing.md` §12 第 1 条写着「产品**不引入衬线**」。本文推翻它。

**推翻的理由**：品牌识别度的大头在标题字形上。中性底 + Iris 只做到「同一个色系」，衬线标题才做到「同一个品牌」—— 一个用户从 landing 点进产品，如果标题字形换了族，前面所有的配色对齐都会被这一下抵消掉。

**代价比预想的小得多，因为字体已经在了**：

| 项            | 原以为                               | 实际                                                                                                                               |
| ------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 依赖          | 要装 `@fontsource-variable/fraunces` | **无需新增** —— `package.json:17` 已有 `source-serif-4`                                                                            |
| 构建          | 要加 `@import`                       | **无需** —— `styles.css:15` 的 `@import` 是**全局的**，不在 `.landing-root` 作用域内，字体已经在 webapp 的 CSS 里声明              |
| webapp 运行时 | +121KB                               | **119KB（latin 子集），且与 landing 共享缓存** —— 从 landing 进来的用户已经下载过。`@font-face` 是懒加载的，所以只有真的用到才下载 |
| docs 运行时   | +121KB                               | **+119KB** —— docs 是独立 bundle，这一份是真的新增，需要装依赖                                                                     |
| CJK           | 回退宋体                             | 不变，仍然回退宋体                                                                                                                 |

也就是说：**webapp 侧的衬线迁移是零依赖、零构建改动**，只是把一个已声明的族指给几个档位。docs 侧才需要装包。

### 4.2 24px 门槛：换字体之后它的理由变了

把 T1 的 24px 门槛套到产品的三档显示模式上：

| 档位           | compact | default | large |
| -------------- | ------- | ------- | ----- |
| `text-display` | 28      | 32      | 36    |
| `text-h1`      | 20      | 22      | 24    |
| `text-h2`      | 18      | 20      | 22    |
| `text-h3`      | 16      | 18      | 20    |

docs 是单列：display 40 / h1 30 / h2 22 / h3 18。

**门槛对 Source Serif 4 不成立。** Measured on macOS Retina [2026-09-02]（`.product-iris.preview.html` §04 逐档对照）：Source Serif 4 在 22 / 20 / 18px 上笔画完整、稳定，与 Geist 并排看没有质量差距 —— 它本来就是正文衬线。Fraunces 在同样字号下会明显发虚，那才是 T1 那条线的来源。

**所以门槛不再是「会碎」的问题，而是「语域」的问题**：

- **h2 / h3 仍然建议留在 Geist**，理由是它们是密集工作面上的**小标题**，读者需要快速扫过判断层级；衬线会让扫读变慢。这是设计选择，可以讨论。
- **h1 不再需要为了过门槛而提号**。这直接催生了下面的 S3。

低 DPI Windows 的风险随之下降但没消失 —— Source Serif 4 的容错比 Fraunces 大得多，但仍应在 1× 屏上看一次（§8）。

### 4.3 裁决：三个方案

|                   | webapp                                         | docs                   | 动既有裁决吗                     |
| ----------------- | ---------------------------------------------- | ---------------------- | -------------------------------- |
| **S1**            | `text-display` (28/32/36)                      | `display` 40 + `h1` 30 | 否                               |
| **S2**            | + `text-h1` 提到 **24**/26，compact 回落 Geist | 同 S1                  | **是**（推翻 C2「22px 天花板」） |
| **S3** _新，推荐_ | + `text-h1` **留在 22**，直接用衬线            | 同 S1                  | 否                               |

**S3 是换字体之后出现的新选项，也是现在最可能正确的那个。** S2 的全部理由是「22px 过不了 Fraunces 的门槛所以要提号」；Source Serif 4 没有这个门槛，提号就失去了依据，而 C2 那条既有裁决（22px 是页面标题天花板）可以原封不动地留着。

**mock 顶部四个开关（不用 / S1 / S2 / S3）可以直接切**，底部有三者的并排对比。

字重与族参数全部对齐 `--lp-display-*`：

| 参数                | 值                                                                                                | 来源                            |
| ------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------- |
| family              | `'Source Serif 4 Variable', 'Source Han Serif SC', 'Noto Serif SC', 'Songti SC', 'SimSun', serif` | `styles.css:2156`               |
| font-weight         | **400**，所有档统一                                                                               | `--lp-display-weight`           |
| font-optical-sizing | `auto`                                                                                            | landing 同                      |
| text-wrap           | `balance`                                                                                         | landing 同                      |
| 可变轴设置          | **无** —— 不要写 `font-variation-settings`                                                        | Source Serif 4 只有 opsz + wght |

> **不要写 `font-variation-settings: 'SOFT' 50, 'WONK' 0`。** 那是 Fraunces 的轴，Source Serif 4 上它是**静默无效**的。这个 mock 的第一版就踩了这个坑：Google Fonts 按请求的轴做子集，返回的文件根本不含 SOFT 轴，CSS 里的声明看着对、实际不起任何作用，肉眼几乎察觉不到。

**Geist 的 500 字重上限不变**。衬线固定 400 是另一条独立规则，作用在不同的族上。

顺带修一个既有违规：**docs 的 h1/h2/h3 现在是 600 字重**，明确违反 §5 的「产品面上限 500，never 600」。h1 换衬线后落到 400；h2 / h3 / h4 **一并降到 500**。

### 4.4 tracking 与 line-height

landing 的曲线是：大字 −0.018em / lh 1，到 h3 档（24–29px）放松到 −0.008em / lh 1.14。产品的档位全部落在 landing h3 档附近或更小，所以取值靠近后者：

| 档                        | 现状 tracking | 改成         | 现状 lh | 改成                  |
| ------------------------- | ------------- | ------------ | ------- | --------------------- |
| docs `display` 40         | −0.025em      | **−0.014em** | 1.05    | **1.15**              |
| docs `h1` 30              | −0.02em       | **−0.014em** | 1.1     | **1.15**              |
| webapp `text-display` 32  | −0.025em      | **−0.012em** | 1.15    | **1.12**              |
| webapp `text-h1` 22 或 24 | −0.02em       | **−0.008em** | 1.25    | **1.2**（S3 用 1.22） |

未改用衬线的档（h2 / h3 及以下）**tracking 与 lh 全部不动**。

### 4.5 CJK

landing 的实际写法（`styles.css:3721`）是 `html[lang^='zh'] .landing-root .lp-h*`，产品对应写成：

```css
html[lang^='zh'] .text-display,
html[lang^='zh'] .docs-h1 {
    word-break: keep-all;
    letter-spacing: 0;
    line-height: 1.15;
}
```

三条都要，**`word-break: keep-all` 别漏** —— 它是 landing 实现里有、文档里没写的一条。

**Windows CJK 的 `data-cjk-weights="coarse"` 机制不受影响** —— 它只钉 `<strong>` 的字重，与 display 族无关。

### 4.6 不变的东西

- **字号阶梯本身** —— S1 / S3 完全不动，只有 S2 动 h1 一档。
- **`--text-chat` 契约**（composer 与消息体同号）。
- **markdown 标题降一档规则**。markdown 标题**不用衬线**：它们身处 14px 正文流中，换族会破坏阅读流。
- **`Geist Mono` 的职责**不变。
- **代码永远 400 字重。**

## 5. 圆角：8 / 10 / 14 → 6 / 8 / 12

### 5.1 裁决

**方向与色彩相反：圆角不向 landing 靠，而是继续收紧。**

| 档         | 产品现状          | 改成   | landing | 用在                                                 |
| ---------- | ----------------- | ------ | ------- | ---------------------------------------------------- |
| `xs`       | 8                 | **6**  | 8       | code chip、小 input、tag（19 处）                    |
| `sm`       | 10                | **8**  | 12      | 按钮、控件、被包裹的菜单项（110 处，其中 button 27） |
| `md`       | 14                | **12** | 16      | 卡片、面板、popover（208 处，其中 div 119）          |
| `lg`–`3xl` | 20 / 24 / 28 / 32 | 不动   | 同      | 产品不取                                             |

`--radius-pill` 9999 不动。

**这不是「对齐 landing」，是第三轮收紧。** `DESIGN.md` §6 记着前两轮：20/16/12 → 18 → 14。这一轮到 12，理由同前两轮 —— 密集工作面上大圆角读起来 bubbly；差别只是这次连 `xs` 一起降，因为 `sm` 落到 8 之后会与旧的 `xs` 撞值。

于是产品与 landing 的圆角差距从 2 拉到 4（`sm` 8 vs 12、`md` 12 vs 16），**两套 scale 只在 `xs` 之外的上层四档相同**。这是知情的：色彩与字体向 landing 收敛做品牌统一，圆角反向发散做密度区分 —— 同一个品牌在两种密度下本就该有不同的形状语言，`DESIGN.md` §6 的「两个体积」正是这个意思。

### 5.2 同心圆角：主模式完好

嵌套元素的圆角 = 父级圆角 − 内距。全站扫描「外层圆角 + 内距」的组合，结果如下：

| 组合                         | 处数   | 现状所需内层  | 新 scale 所需内层 |
| ---------------------------- | ------ | ------------- | ----------------- |
| `rounded-md` + `p-1`         | **25** | 10px = `sm` ✓ | **8px = `sm` ✓**  |
| `rounded-md` + `p-3` / `p-4` | 29     | ≤ 2px         | ≤ 0px             |
| `rounded-sm` + `p-2.5`–`p-4` | 6      | ≤ 0px         | ≤ 0px             |
| `rounded-md` + `p-2.5`       | 1      | 4px 无此档    | 2px 无此档        |

**第一行是唯一真正构成「外层完美包裹里层」的模式**（popover / 菜单 / segmented），25 处，而它**继续完美同心** —— 因为 `sm` 与 `md` 同时降 2，差值仍是 4，正好等于 `p-1`。实测 `AppShell.tsx:1784` 的用户菜单：现状 `14 − 4 = 10`，新 scale `12 − 4 = 8`，两者都分毫不差。

其余组合的内距都 ≥ 10px，子元素离边缘远，不构成包裹关系，同心规则本就不适用。

> **一个既有的 0.5px 偏差，不是本轮引入的。** 内距 `p-1` 是 `rem`，圆角是 `px`，而 root font-size 随显示模式变（14 / 16 / 18px）。所以 `p-1` 实际是 3.5 / 4 / 4.5px，只有 `default` 完美同心，compact 与 large 各差 0.5px。改前改后同样偏差，圆角上看不出来。真要根治，把 popover 的内距写成 `p-[4px]` —— 那是一次独立的小修，与本轮无关。

### 5.3 例外：chat composer 保持 18px

`styles.css:763` 把 composer 钉在 18px，是 `DESIGN.md` §6 的明文例外 —— 主输入要读作柔软、可触的控件。

**本轮保持 18，但要知道例外的性质变了**：它原先高出 `md` 4px（18 vs 14），现在高出 6px（18 vs 12）。也就是说 composer 会比迁移前更显眼地"软"。这是可接受的 —— 那个例外的存在意义正是让主输入从周围的方硬卡片里脱出来，反差变大反而强化了意图。

如果后续觉得 6px 落差过头，收到 14 仍然高出 `md` 一档，比例与现在的 18 vs 14 相当。**不要收到 12** —— 那等于取消例外，得先推翻 `DESIGN.md` §6 那条裁决。

2. **切品牌别名**（§2.2）。`--color-info` / `-strong` / `-bg` / `-vivid` / `-focus` / `-link` 指向 Iris。此步全站蓝色变化，**是最显眼的一步，单独一个 commit**。

4. **Ash 化中性轴**（§1.2 / §1.3）。浅深两组，一次改完 —— 拆开会出现半迁移的怪配色。

7. **接通 display 族**（§4.3）。**webapp 无需装任何东西** —— `styles.css:15` 已全局 `@import` Source Serif 4，只要加 `--font-display` 与 Tailwind family。**docs 侧要装**：`pnpm --filter @manyfold/docs add @fontsource-variable/source-serif-4`。
8. **接衬线档**（§4.3）。先上 S1（webapp `text-display` + docs `display`/`h1`），tracking 与 lh 同步改（§4.4），CJK 覆盖一起加（§4.5，别漏 `word-break: keep-all`）。

10. **（可选）S3 或 S2**：给 webapp `text-h1` 接衬线 —— S3 留在 22px（推荐，不动既有裁决），S2 提到 24px 并让 compact 回落 Geist。**只在 mock 验证通过后做。**

每一步之后跑 `pnpm check && pnpm lint && pnpm knip`。

> **`governance:check` 跑不到 oss 的 PR 上 —— 这一点容易踩空。** 脚本只存在于**父仓**（`scripts/check-governance.mjs`，父仓 `package.json` 的 `governance:check`）；`oss/package.json` 里**没有**这个脚本。它通过 `coreApp()` 跨仓读取 `apps/web/src/styles.css` 与 `apps/docs/src/styles/global.css` 两份基线，比对 `--shadow-focus` 的配方与 halo alpha 是否成对一致（`focusRingTokenFailures`，`scripts/check-governance.mjs:658`）。
>
> 后果：**在 oss 分支上跑 `pnpm governance:check` 会直接报「找不到脚本」**，而 oss 的 PR CI 也不跑它。这个门禁只在 oss-bump 把 submodule 指针 PR 回父仓时，由父仓 CI 的 contract-CI leg 触发 —— 也就是说**违规会在合入公共仓之后才被发现**。
>
> 本轮不改 `--shadow-focus` 的配方（只有 `--color-focus` 的取值变），所以风险低。但要在本地先验的话，做法是：在 oss 分支上改完，回到父仓根跑 `pnpm governance:check`（它读的就是工作区里的 `oss/` 文件）。

## 10. 四个不在本轮的问题

### 10.1 `DESIGN.landing.md` §2.2–§2.4 需要一个修正 PR

那三节描述的字体（Fraunces / SOFT 50 / WONK 0 / 字重 300 / tracking −0.014em / lh 0.98）与 `src/styles.css` 的实现（Source Serif 4 / 无可变轴 / 400 / −0.018em / 1）**整段不符**，见 §4.0 的对照表。字号阶梯是对的，其余全错。

这不在本轮范围，但**应该尽快单独修**，因为它正在误导实现：本文档的第一版就是照着它写的，mock 的第一版也照着它加载了 Fraunces 并写了 `SOFT 50` —— 而那个声明在 Source Serif 4 上静默无效，肉眼几乎察觉不到。**任何照着那三节写代码的人都会踩同一个坑。**

修的时候连带确认两处文档里没有、实现里有的东西：`text-wrap: balance`（`styles.css:2379`）与 CJK 的 `word-break: keep-all`（`styles.css:3725`）。

### 10.2 `DESIGN.landing.md` §1.4 的判定色表也是错的

那张表的表头是「浅色 fill / text」，把 `#22c46f` / `#e9a23b` / `#f2554b` 列成浅色的 fill 档。**代码里没有浅色 fill 档** —— 浅色的 `--lp-success` 就是单值 `#12a75c`；那三个 hex 实际是**深色模式的 `-strong`**（`styles.css:2293/2296/2299`）。

同一节还写着 `fill = 500 · numeral = 400 · label = ink-3` 这条「一支色两个亮度」的规则，读起来像是浅色也有两档 —— 实际上代码里的三档是 `-{hue}` / `-bg` / `-strong`，没有 fill/numeral 的分离。

顺带：`-bg` 的 alpha 在表里没写，实际是 info .10 / success .10 / warning .10 / **error .09** / **idle .13**，深色另一组。

### 10.3 `styles.css` 的 `.landing-root` 注释自相矛盾

`styles.css:1994` 的注释写着 _Only 2–4 units of cool bias (B a little above R) to cancel the yellow cast of warm displays; no hue is readable_。但同一个块里往下 20 行，`--lp-muted: #5c5e66` 的 B−R 是 **10**，`--lp-subtle: #8d8f97` 也是 10。

那句话只对**背景五档**成立。这条注释就是本文档 §1.2 那个坑的源头 —— 它读起来像是整个 Ash 系统的规则。建议改成「背景档 0–3 单位，墨阶在中灰区最多 10 单位」。

### 10.4 两份文档最终要合并

`DESIGN.md` 与 `DESIGN.landing.md` 迁移完成后会有大量重复内容（阴影解剖、运动、状态矩阵、链接规则都变成逐字相同）。`DESIGN.landing.md` §12 第 4 条要求那时把两份文档合并。

**不要在本轮做。** 合并要动 1678 + 1080 行，会把真正的视觉 diff 完全埋掉。正确顺序是：迁移落地 → 观察一到两个发布周期 → 单独一个纯文档 PR 合并。本文档在那次合并里一并归档。
